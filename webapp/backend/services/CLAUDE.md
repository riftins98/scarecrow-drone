# services

Business logic layer. Services coordinate repositories and external resources (subprocesses). Two categories of service live here:

- **Subprocess services** (sim_service, detection_service): manage long-running external processes. Stateful — hold PID, running flag, parsed stdout. Not easily unit-tested.
- **Business services** (flight, drone, area_map, chase_event, telemetry, recording): pure orchestration over repositories. Fully unit-testable.

## Files
- `__init__.py` — Re-exports all services for `from services import *`
- `sim_service.py` — `SimService`: manages PX4+Gazebo lifecycle. Module-level `_skip_px4_build()` decides whether to pass `--no-build` to the launcher: it does so whenever `px4/build/px4_sitl_default/bin/px4` exists (override with `SCARECROW_FORCE_BUILD=1`), so only a never-built clone triggers a build. This is required for correctness on the pixi track — `launch.sh`'s `make px4_sitl` runs CMake without the flags in pixi.toml's `build` task and dies on protobuf 35's deprecated `RepeatedField::Resize` under `-Werror`, so "Connect" used to destroy a working build. Module-level `_port_in_use(port)` does a `socket.bind` probe, replacing an `ss -tln` subprocess that was Linux-only and turned every macOS camera swap into a 500. `switch_camera()` respawns the streamer with `sys.executable` rather than `.venv/bin/python` (pixi has no `.venv`). `launch(world, headless, camera, spawn)` spawns the bash launcher (`launch.sh` for GUI or `launch_with_stream.sh --headless --no-open --<camera>`) as a subprocess. Tracks the 11-stage launch progress, captures the stream URL from the headless banner, and keeps a stable subprocess reference in the watcher thread so `stop()` cannot race it into `None.poll()`. `stop()` kills `gz sim`, tears the PX4 instance down via module-level `_kill_px4_instance()` and kills `stream_camera`, resets `headless`/camera/stream state, clears the launcher log buffer, and sweeps flight scripts. `reset_drone_pose()` is the panic-reset teleport: discovers the running drone model (`_discover_drone_model()` via `gz model --list`, prefix `holybro_x500`) and calls the world's `set_pose` service to snap it back to the session spawn. Spawn location is configurable for any mapped world: `launch(..., spawn={x,y})` validates against the SDF-derived spawn map from `world_geometry.py` (>=2m from walls and clear of static obstacle footprints), then sets `_spawn_pose`; `set_spawn(x,y)` re-spawns on a running sim and updates where reset returns. `drone_pose()` queries the drone model's live world pose for the minimap. `disarm_via_console()` and `reset_drone_values_via_console()` write commander commands through the launcher's pxh FIFO first, falling back to the subprocess stdin pipe. FIFO path is POSIX-only. Module-level `_kill_px4_instance()` / `_px4_alive()` reap **every** part of a SITL instance: `pkill -x px4` alone left `px4-mavlink` (a `px4-<module>` client whose process name is not "px4") and the `/bin/sh .../init.d-posix/rcS` startup shell running, so the next Connect hit `ERROR [px4] Task already running`, never brought the estimator up, and the drone refused to arm with "Preflight Fail: ekf2 missing data" — an error that points at the EKF rather than the leftover process. It escalates to SIGKILL and **waits**, because `launch()` starts ~1s later and a dying process still holds the instance. `switch_camera()` respawns `scripts/stream_camera.py` — the same streamer the launcher runs, and the only one — so a camera swap cannot change transport mid-session and freeze the browser's picture.
- `world_geometry.py` — SDF parser for spawn maps. Reads `worlds/*.sdf` plus included `models/*/model.sdf`, derives the full floor rectangle from floor/ground collision geometry, insets it by `SPAWN_WALL_MARGIN`, collects static obstacle footprints (camera models ignored), and exposes `spawn_map_for_world()`, `all_spawn_maps()`, and `validate_spawn(world, x, y)`.
- `detection_service.py` — `DetectionService`: spawns a chosen script in `scripts/flight/` as an unbuffered Python subprocess (`sys.executable -u`, `PYTHONUNBUFFERED=1`) so stdout streams consistently on macOS/Linux/WSL/Windows. Prepends `REPO_ROOT` to the subprocess `PYTHONPATH` — running `scripts/flight/x.py` puts `scripts/flight` on `sys.path`, not the repo root, so every `from scarecrow...` failed under pixi (the venv track got this from `pip install -e .`, Docker from `ENV PYTHONPATH`). `start(flight_id, on_detection, script_name="demo_flight_v2.py", script_args={})`: validates the script exists under scripts/flight/, formats the dict into argparse-style `--flag value` CLI tokens (bool True -> bare flag, bool False / None / "" -> skipped), and always appends `--flight-id` unless the user already supplied it. Background thread parses stdout protocol: `DETECTION_IMAGE:` (tracks image path + triggers on_detection callback), `TELEMETRY:{json}` (merged, not replaced, into `latest_telemetry`), `VIDEO_PATH:`. It also mines plain log lines via `_parse_log_extras()` for `phase` (`--- Phase N: ... ---` banners), `agl`, `ceiling`, `leg`, lidar distances (`front`/`left`/`right`/`rear`/`wall`, with `inf`→None), commanded velocities (`fwd`/`lat`/`yaw`), pursuit outcome (`target`/`target_dist`), wall-follow `stop_reason`, and `fps`, merging them into `latest_telemetry` so the telemetry rail can show per-script live readouts. The pure parser is unit-tested in `tests/unit/webapp/services/test_detection_log_parser.py`. `stop()` detaches rather than kills -- the flight script handles its own landing. `kill()` (panic path) group-kills the subprocess tree immediately so it stops commanding the drone before a reset/teleport, then clears all per-flight state. Flight scripts are spawned with `start_new_session=True` (own process group) so `kill()` can `os.killpg` the script + its child mavsdk_server together — otherwise the server outlives a killed script and squats on udp 14540, blocking the next flight. `start()` and `kill()` both call module-level `_sweep_flight_processes()` (tightly-scoped `pkill` of `scripts/flight/*.py` and `mavsdk_server`; POSIX-only) as a backstop so an orphaned run can never block the next one. `sim_service.stop()` does the same sweep so tearing the sim down mid-flight can't orphan a script.
- `script_metadata.py` — Introspects flight scripts and worlds for the webapp's pre-flight pickers. `list_worlds(worlds_dir)` enumerates `*.sdf` and attaches stream camera options derived from `scripts/shell/launch_with_stream.sh` (merged with SDF camera model metadata when present). `list_flight_scripts(scripts_dir)` runs `python3 <script> --help` (subprocess, never imports the script — flight scripts have heavy side effects) and parses argparse output into typed `ScriptArg` records (str/int/float/bool/choice). Scripts that don't use argparse or have heavy import-time logic time out cleanly; the resulting ScriptInfo carries a `parse_error` and the UI falls back to "no parameters."
- `stream_cameras.py` — Canonical stream camera list used by `/api/sim/cameras` and `SimService` validation. The webapp exposes Fixed, Drone Camera, and Drone View; the legacy shell `--center` flag remains available for manual launcher use but is not offered in the UI.
- `flight_service.py` — `FlightService`: flight lifecycle (create_flight, start_detection, stop_flight, abort_flight, get_flight_summary, delete_flight). Coordinates FlightRepository + TelemetryRepository + DetectionService.
- `drone_service.py` — `DroneService`: wraps DetectionService with drone-specific API (get_status, start_flight, stop_flight, abort, return_home, get_telemetry). `force_disarm()` (panic path) connects to the SITL MAVSDK endpoint on a private event loop and issues `action.kill()` (falling back to `disarm()`) so the autopilot won't fly back up after a teleport — best-effort, returns False on any failure. Phase 6 (UC7) will extend with SIGTERM handling.
- `area_map_service.py` — `AreaMapService`: CRUD for area maps + mapping session state (start_mapping is stubbed for Phase 3 UC1).
- `chase_event_service.py` — `ChaseEventService`: chase event lifecycle for UC5. Validates counter_measure_type (pursuit/movement/combined) and outcome (dispersed/lost/aborted).
- `telemetry_service.py` — `TelemetryService`: per-flight telemetry tracking (battery, distance, detection count). 1:1 with flights.
- `recording_service.py` — `RecordingService`: video recording status for UC3. The actual PNG+ffmpeg pipeline lives in GazeboCamera; this service just tracks recording state for the webapp.

## Subprocess stdout protocol
Flight scripts communicate with services via stdout lines parsed by the monitoring thread:
- `DETECTION_IMAGE:/path/to/img.png` — parsed by DetectionService (implemented)
- `MAP_RESULT:{"map_path":"..."}` — mission map JSON path; persisted on `flights.map_json_path` and rendered on demand via `mission_map_service.py` + `GET /api/flights/{id}/map/image`
- Future (Phase 4-6): `CHASE_START:type`, `CHASE_END:outcome`, `ABORT_REQUESTED`
